- **DMA中断优先级**:ADC读取电位器电阻的时候，因DMA中断优先级小于FreeRTOS中断最大值导致任务调度频繁被DMA抢断，从而让任务卡死
```c
#define configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 5
```
**解决**：通过单步调试并用LED亮灭定位到，当调度器启动中断时，主控触发高优先级中断从而卡死调度器。而非任务栈过小或硬件通路
- **未编写保险**：对遥控数据解析没有实现当通讯断路时，无人机端应及时响应如停转或怠速，血泪教训，差点似了喵

[状态机任务](FlightControl/apps/Tasks/Task_status.cpp)

**解决**：前期通过C,编写简单状态机驱动，后期单独完成Status_Task,利用C++的强类型枚举，防止编译器读取错误的状态

- **NRF24L01全双工通信**：发送函数因接收函数堵塞导致发送函数卡死

**解决**：利用FreeRTOS信号量、互斥锁等，将发送端与接收端独立，防止未接收完全数据导致Status不全或随机值

[NRF24L01](FlightControl/drivers/NRF24L01/NRF24L01.cpp)

## CPP的引入
最开始我是没打算加入c++的,但是c的底层确实看了头皮发麻,目前我只引入C++17的特性,inline、constexpr,在Debug模式下,这些作用和效果微乎其微,因为编译器的缘故,在released条件下,flash优化可以达到百分之三十三左右,基于F407这种比F103有较高的性能。

C++能够充分展示其优雅的手段，比如说零抽象开销[BSP_GPIO](FlightControl/bsp/stm32f407/bsp_gpio.hpp)与优雅的上层接口。从最开始了解到CPP模版的魅力,到现在学习再封装HAL库,这是一个对MCU开发者来说可能并不值得的技术,MCU并不是什么高大上的事物,微控制器只是嵌入式的一个很小的入门,不管是linux,还是FPGA,能使用CPP,Python转义verilog等上层开发的语言，还是micropython，这些都是越来越降低开发的门槛，让开发变得简洁,

~~虽然也没简洁多少~~

## 对AI的看法？

实不相瞒，确实有使用过AI来修改代码或者参与开发，但是我发现好像没啥用啊。

每次都是我自己思考良久才发现错误的成因——这是我还停留在普通LLM的使用的认知，使用过agent后，我对他是非常敬畏的，即使copilot挺忙的，但是好像确实很忙，找他修改一些BUG总是会找错方向，但是的确是能解决部分问题，我只是让他分析一些项目中一些不足，并让他初步尝试修改简单的问题，我的工程就不管用了。

比如说修改iic总线繁忙的问题，没修之前就是简单的任务抢占资源的矛盾，改了之后好像是直接让另一个任务死掉了。小型任务的确方便，但是工程不可能全靠一个人来完成，AI的加入无疑是让整个项目的不确定性放大了，我们能够预判同事的习惯，却不能了解AI的思路，毕竟都是算法与拟合，它可以是任何一个人。

SKILL对我来说其实并不能提高太多效率，本质上就是个角色扮演罢了。总的来说AI绝对不是普通的生产工具这么简单，他让事物的发展有了更多的方向，是一种发散的结果，枚举神力，但同时和大多数工具一样，必先利其器，写作业真好用罢(
